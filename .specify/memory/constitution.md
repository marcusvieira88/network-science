# Enron Network Case Constitution

A headers-only, privacy-first analysis pipeline over the public Enron email corpus, built as an
engineering case study. The corpus is public; the pipeline is built as if it were not.

## Core Principles

### I. Content Never Enters the System (NON-NEGOTIABLE)

- The parser MUST stop reading each message at the end of the header block. Bodies and
  attachments MUST never be read into memory, persisted, or logged.
- Header fields are admitted only through an explicit allowlist. Every field not on the allowlist
  is dropped at the parser and never reaches any later stage.
- `Subject` and every other free-text header are classified as content and MUST be dropped.
- The allowlist, with the reason each field is in or out, MUST be documented in one place and
  enforced by automated tests, including a canary test that plants marker strings in bodies and
  subjects and asserts they appear in no artifact, log, or report.

Rationale: this is the one hard rule of the brief and the trust model of the real product. A rule
that is only a convention will be broken by the first careless change.

### II. Privacy by Design

- Direct identifiers (addresses, display names, mailbox owner folder names) MAY exist only inside
  a clearly bounded ingestion zone. Everything downstream of the pseudonymization boundary MUST
  see pseudonyms only.
- Pseudonyms MUST be keyed, stable across runs for the same key, irreversible without the key,
  and consistent with identity resolution (one resolved person → one pseudonym).
- The key MUST never be committed, logged, or written to an output artifact.
- Every published table or figure MUST meet a stated minimum group size (k). Cells below k are
  suppressed or coarsened, never published.
- Re-identification risk MUST be measured by an actual attack against the pipeline's own output,
  not asserted.

Rationale: pseudonymization alone does not anonymize a network; structure re-identifies people.
The design has to assume an informed adversary.

### III. Reproducible End to End

- One command MUST take a clean checkout from raw corpus to final report.
- Dependencies MUST be pinned with a lockfile. All randomness MUST be seeded and the seed
  recorded in the output.
- Each stage MUST write its output with a content hash and a manifest of inputs, so two runs with
  the same inputs and key produce byte-identical analytical outputs.
- Numbers in the report and the presentation MUST be generated by the pipeline, never typed by
  hand.

### IV. Specified and Tested Algorithms

- Every metric and transformation MUST have a written definition before it is implemented.
- Every algorithm MUST be tested against synthetic data with known ground truth, in addition to
  being run on the real corpus.
- Identity resolution and deduplication MUST report measured precision/recall on a labelled
  sample or synthetic set, not just counts.
- Results that depend on a threshold or parameter MUST come with a sensitivity check.

### V. Honest Limits

- Every finding MUST state its evidence, a confidence level, the alternative explanations
  considered, and what would falsify it.
- Known biases of the data (about 150 mailboxes, senior staff, survivorship in what was retained)
  MUST be stated next to the results they affect.
- The decision record MUST name what is unknown or was not done, and why.

### VI. Spec-Driven, Agent-Built, Human-Accountable

- Work proceeds spec → plan → tasks → implementation. Code without a task traceable to the spec
  MUST NOT be merged.
- Modules communicate only through versioned data contracts (schemas), so independent agents can
  build them in parallel without sharing internals.
- Agent output is accepted only through gates: tests, type checks, lint, the privacy canary, and a
  review by an agent or person that did not write the code.
- The AI workflow MUST be recorded as it happens (what was delegated, what was rejected, what was
  verified and how), because it is itself a deliverable.

### VII. Simplicity Over Polish

- The working budget is 12 hours, inside the brief's 24-hour window. Scope is the four tasks of the brief and its four deliverables.
- Prefer a clear table to a dashboard, a single process to a service, a file to a database server.
- A feature not required by the brief MUST be justified in the plan's complexity tracking or
  left out.

## Privacy & Data Handling Constraints

- Raw corpus and any artifact containing direct identifiers live under a git-ignored directory and
  MUST never be committed.
- Only pseudonymized, k-thresholded outputs MAY be committed or shown.
- Logs MUST contain counts and pseudonyms only; logging an address, name, or header value from
  the ingestion zone is a defect.
- The repository MUST document what would change with real customer data (key custody,
  retention, works council review, data residency), even where the case does not implement it.

## Development Workflow & Quality Gates

- Documentation of flows and architecture uses Mermaid diagrams, kept in the repository next to
  the text they explain.
- Each task names the files it owns. Two tasks running in parallel MUST NOT own the same file.
- A change is done when: its tests pass, the full gate (lint, types, tests, canary) passes, and
  the relevant spec/plan/contract documents still describe what the code does.
- Architectural choices with a real alternative are recorded as short decision entries
  (context, decision, trade-off).

## Governance

This constitution takes precedence over other practices in this repository. Plans and task lists
MUST include a constitution check and record any justified deviation. Amendments are made by
editing this file with a version bump (MAJOR: principle removed or redefined; MINOR: principle or
section added; PATCH: clarification) and a one-line reason in the commit message. Reviews verify
compliance with Principles I and II first; a violation of either blocks the change regardless of
other merits.
